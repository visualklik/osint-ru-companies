# Схема базы

Одна SQLite-база, по умолчанию `data/corp.db`. Путь переопределяется через
`--db` или переменную окружения `RU_CORP_DB`. Схема создаётся при первом
подключении, `CREATE TABLE IF NOT EXISTS` — повторный запуск безопасен.

Все таблицы независимы: если какой-то модуль не запускали, его таблица просто
пуста, и отчёты это переживают.

## Организации и люди

### `orgs` — карточка юрлица
Заполняет `crawl.py` из выписки ЕГРЮЛ.

| Поле | Что |
|---|---|
| `inn` | ИНН, первичный ключ |
| `ogrn`, `kpp` | реквизиты |
| `name_short`, `name_full` | наименования |
| `status` | «действующее» либо формулировка из выписки о прекращении или реорганизации |
| `reg_date` | дата регистрации |
| `address` | юридический адрес как в ЕГРЮЛ |
| `address_key` | нормализованный ключ «улица + дом», см. ниже |
| `okved`, `okved_name` | основной вид деятельности |
| `capital` | уставный капитал, рубли |
| `region` | регион из строки поиска |
| `fetched_at` | unix-время загрузки |
| `raw` | вся разобранная выписка в JSON, включая полный список ОКВЭД, лицензии и филиалы |

### `persons` — физические лица
| Поле | Что |
|---|---|
| `pid` | ключ: личный ИНН, если известен, иначе `fio:<нормализованное ФИО>` |
| `inn` | личный ИНН |
| `fio` | ФИО как в выписке |
| `fio_key` | ФИО в верхнем регистре, ё заменена на е |

### `roles` — должностные лица
`(org_inn, pid, role)`, плюс `grn` и `since`. Роль — как записана в ЕГРЮЛ:
«ГЕНЕРАЛЬНЫЙ ДИРЕКТОР», «ЛИКВИДАТОР» и так далее.

### `ownership` — владение и управление
| Поле | Что |
|---|---|
| `org_inn` | кем владеют |
| `pid` | владелец-физлицо, либо пустая строка |
| `owner_inn` | владелец-юрлицо, либо пустая строка |
| `kind` | `owner` — доля в капитале, `manager` — управляющая организация |
| `share_pct`, `share_rub` | размер доли |
| `grn` | номер записи ЕГРЮЛ |

Первичный ключ включает `kind`, потому что одно и то же юрлицо бывает
одновременно и участником, и управляющей организацией — это разные связи.

Вместо NULL в ключевых полях стоят пустые строки: SQLite не считает NULL
равными друг другу, и `INSERT OR REPLACE` переставал бы дедуплицировать.

## Финансы и налоги

### `financials` — строки форм 1 и 2
`(inn, year, code)` → `value`. Код — номер строки отчётности: 2110 выручка,
2400 чистая прибыль, 1300 капитал, 1600 активы и так далее. **Значения в
рублях** — модуль переводит их из тысяч на входе.

### `headcount` — среднесписочная численность
`(inn, date)` → `count`. Из выгрузки `sshr2019`.

### `tax_debt` — задолженность
`(inn, date, tax)` → `debt`, `penalty`, `fine`. Из выгрузки `debtam`.

### `revexp` — доходы и расходы
`(inn, date)` → `income`, `expense`. Из выгрузки `revexp`. Независимый источник
против ГИР БО.

### `tax_regime` — спецрежимы
`(inn, date)` → `regimes`, строка вида «УСН» или «ОСНО». Из выгрузки `snr`.

### `opendata_loads` — что загружено
`dataset` → `url`, `rows`, `loaded_at`. Чтобы не гадать, какие наборы уже есть.

## Рабочие места

### `sout` — декларации СОУТ
Одна строка на должность.

| Поле | Что |
|---|---|
| `inn`, `decl_date` | компания и дата внесения декларации в реестр |
| `address` | **фактический** адрес осуществления деятельности |
| `address_key` | нормализованный ключ |
| `wp_number` | индивидуальный номер рабочего места |
| `position` | профессия или должность |
| `headcount` | численность на этом рабочем месте |
| `sout_org`, `valid_until` | кто проводил оценку и до какого срока действует |

Номера, должности и численность приходят тремя параллельными списками через
запятую. При расхождении длин численность не проставляется — лучше пусто, чем
разнесено наугад.

## Надзор и суды

### `inspections` — ЕРКНМ
`(inn, number, year, month)`. Номер мероприятия, тип, вид контроля, орган
контроля, орган прокуратуры, статус, сроки. Ключ включает год и месяц выгрузки,
поэтому повторная загрузка того же месяца идемпотентна.

### `court_cases` и `court_parties` — арбитраж
Дело хранится отдельно от сторон, потому что сторон в деле много и у части из
них нет ИНН. `court_parties` — `(case_id, name, side)`, где `side` это «истец»,
«ответчик» или «иное».

## Обратный поиск

### `person_orgs` — компании человека
`(pid, inn, role)`. `pid` — личный ИНН. Роль, доля, телефоны, адрес, статус,
`source` — из какого агрегатора. **Это лиды, а не реестровая истина**: данные
агрегаторов отстают, каждую компанию надо сверять через `crawl.py add`.

## Служебное

### `crawl_queue` — очередь обхода
`inn` → `depth`, `state` (`pending`, `done`, `error`), `note`. Переживает
перезапуск: упёрлись в `--limit` — запустите `crawl.py expand`.

### `cases` — метки расследований
`(name, inn)`. Одна компания может входить в несколько дел. Флаг `--case`
у большинства команд фильтрует по этой таблице.

## Нормализация адресов

`db.norm_addr()` сводит адрес к ключу «улица + дом». Всё до названия улицы —
индекс, страна, регион, город, район — отбрасывается, номер помещения тоже.

Причина: один и тот же дом в реестрах пишут десятком способов. Реальные
варианты одного адреса из практики:

```
111111, г. Пример, ул. Ленина, 20/6
г. Пример, ул.Ленина, 20/6
1111112 Примерный край, г. Пример, ул. Ленина, д.20/6
111111, Примерный Край, г.о. Город Пример, г Пример, ул Ленина, д. 20/6
111-1112, ПК, г. Пример, ул. Ленина , д. 20/6, помещение 1
```

Все пять дают ключ `ЛЕНИНА 20 6`. Обратите внимание на опечатки в
индексе — `1111112` и `111-1112`: именно поэтому индекс в ключ не входит.

Соседние дома при этом не склеиваются: 20/6, 25/7, 28/1 и 30/8 остаются
разными ключами.

Улицей считается последний токен без цифр длиннее двух символов, домом — до
двух следующих за ним токенов с цифрами. Из-за этого «Кулакова 27А офис 501»
даёт ключ `КУЛАКОВА 27А 501`, то есть офис попадает в ключ. Для поиска
соседей по зданию это скорее полезно, но знать об этом стоит.

## Нормализация ФИО

`db.norm_fio()` — верхний регистр, ё заменяется на е, лишние пробелы убираются.
Используется как запасной ключ, когда личный ИНН неизвестен.
